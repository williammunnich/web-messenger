# AGENTS.md: for an AI agent working in this repository

You are an AI coding agent and a person has asked you to try out, deploy, embed, update or change Web Messenger.
This file is your briefing. The README and `docs/` are the manuals for people; read them when this is not enough.

## What this project is

Live chat for a website that rings the owner's iPhone. Everything runs in the **person's own AWS account**.

| Part | Files | Runs where |
|---|---|---|
| The service | `aws/chat/src/*.mjs`, one AWS SAM template `aws/chat/template.yaml` | one Lambda function, one DynamoDB table, API Gateway (WebSocket + HTTP), SQS |
| The widget | `aws/chat/src/public/chat.js`, `chat.css` | on the person's website, loaded with one script tag |
| The web inbox | `aws/chat/src/public/inbox.html` | served by the function; Google sign-in, one allowed account |
| The iPhone app | `ios/` (SwiftUI, project generated by XcodeGen) | the owner's phone, installed over the cable |
| Tools | `aws/deploy.sh`, `tools/chat-dev.mjs` (local bench), `tools/smoke.mjs`, `tools/check-public.sh` | the person's computer |

The contract between all parts is `docs/chat-protocol.md`. What a website may rely on is `docs/embed.md`.

## Trying it locally (no AWS account, no cost): start here

```sh
npm install
npm test          # unit tests
npm run smoke     # one real conversation over sockets
npm run dev       # local bench: http://localhost:8790/demo (widget) and http://localhost:8790/ (inbox, signed in)
```

Node 22 or newer. If `npm test` or `npm run smoke` fails on an untouched checkout, stop and report it.

## Deploying it for the person: do this, in this order

Follow `docs/deploy.md`; this is the short form with the points where you must stop for the person.

1. **Settings.** `cp deploy.env.example deploy.env`, then fill it in **with the person**: `ALLOWED_EMAIL` (the one
   Google account allowed into the inbox), `ALLOWED_ORIGINS` (the exact addresses of the sites that will carry
   the widget), `OWNER_NAME`, `SITE_URL`. `deploy.env` is gitignored: never commit it.
2. **Check, changing nothing:** `bash aws/deploy.sh check`. It says what is configured and what is missing
   (AWS CLI, AWS sign-in, settings). The person signs in to AWS themselves; you never handle their AWS keys.
3. **Google sign-in client** (`docs/deploy.md`, step 2): the person creates it in the Google Cloud console and
   gives you only the client id for `deploy.env`. The client secret goes in at the next step, typed by the person.
4. **Secrets:** `bash aws/deploy.sh secrets` asks for the Google client secret (and the Apple push key, if push is
   wanted) and stores them encrypted in AWS (SSM). **The person types or pastes these at the prompt themselves.**
   Never ask for a secret in the chat, never put one in a file, an argument you compose, or a log.
5. **Deploy: ask first.** `bash aws/deploy.sh deploy` creates billable AWS resources in the person's account
   (roughly a dollar a month or less at low traffic; README, "Cost") and IAM roles. Say that, get a clear yes,
   then run it. It runs the tests first and is safe to re-run.
6. **Addresses:** `bash aws/deploy.sh urls` prints the inbox address, the chat address and the script tag. Finish
   the Google client's redirect address as `docs/deploy.md` step 4 says (the person does that in Google's console).
7. **Put the widget on their site** (`docs/embed.md`): the script tag from step 6 plus, if wanted, a
   `window.MESSENGER_CONFIG` block before it. If their site sends a Content-Security-Policy, it must allow the
   chat's addresses. Changing their website is a separate change: show the diff and ask before deploying it.
8. **Check what local tests cannot** with the list at the end of `docs/deploy.md`: a message from the live site
   arrives in the inbox; the reply appears in the widget.
9. **iPhone app (optional):** `ios/README.md`. It needs Xcode, XcodeGen and the person's Apple developer account;
   signing and installing on the phone are done by the person in Xcode.

Updating later: pull, `npm test`, `bash aws/deploy.sh deploy`. Removing: `docs/deploy.md`, "Updating and removing";
deleting the stack deletes stored conversations, so confirm with the person in plain words first.

## Rules for you while working here

1. **Never deploy, delete a stack, or change DNS without a clear yes from the person** for that action.
2. **Secrets never pass through you**: no keys, client secrets or tokens in the chat, in files, in commands you
   build, in commit messages or in logs. `deploy.env`, `ios/Local.xcconfig`, `*.p8` and `.private-patterns` stay
   out of git.
3. **Do not weaken a protection to make something work or a test pass**: the origin list, the bot and rate
   limits, the owner sign-in checks, the rule that email-conversation ids are refused on the visitor side, the
   strict JSON content-type check. If a task seems to need that, stop and explain.
4. **Privacy is part of the product.** The owner sees messages as they are typed, and visitors can see and delete
   their data. If you change what is collected or shown, update the README's "Privacy" section and
   `docs/chat-protocol.md` in the same change.
5. The names a website relies on (`window.webMessenger`, `window.MESSENGER_CONFIG`, the `.msgr` CSS variables and
   the others listed in `docs/embed.md`) are a promise to other people's sites: do not rename or remove them
   without the person deciding to break that promise.
6. Before any push of a fork: `npm run check:public`.

## If you are asked to change the code

- Tests before and after: `npm test`, `npm run smoke`. For the iPhone app: `cd ios && xcodegen`, then build for a
  simulator with `xcodebuild` (do this in a folder that is NOT synced by iCloud, Dropbox or similar).
- Theme: the widget's colours are one block of CSS variables at the top of `chat.css`; the app's are in
  `ios/Messenger/Support/Theme.swift` (README, "Theming").
- Code style: every file starts with a header comment (what it is for, the project, author line, and
  `@date Last edited YYYY-MM-DD`, which you update); every function has a Javadoc-style comment (`@param`,
  `@return`, `@throws`); comments say why. Decisions go in `docs/decisions.md` with the date and the reason.
- Never commit a generated `.xcodeproj`.

## What is not tested (say so if it matters to the task)

The tests run the service against in-memory stand-ins; `npm run dev:dynamo` uses a local DynamoDB. A real AWS
deploy, real Google sign-in and real Apple push are only checked by hand (`docs/deploy.md`, last section).
